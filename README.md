# KrishaBeholder

Сервис мониторинга новых объявлений об аренде квартир на krisha.kz.
Раз в 30 минут (с небольшим случайным сдвигом) обходит заданные поиски и присылает
новые объявления в Telegram.

## Запуск

1. Скопировать `.env.example` в `.env`, вписать `TELEGRAM_BOT_TOKEN`.
2. `docker compose up -d --build`
3. Каждый получатель пишет боту `/start` — бот отвечает его числовым `chat_id`.
   Важно: сообщение боту нужно отправить **после** запуска сервиса
   (история getUpdates хранится недолго).
4. Вписать этот `chat_id` в нужные записи `searches.json` (см. ниже).

Первый обход каждого поиска — «тихая база»: существующие объявления запоминаются
без уведомлений, дальше приходят только реально новые.

## Команды боту

- `/start` — показать свой `chat_id` (чтобы передать администратору для
  `searches.json`) и снять паузу, если рассылка была приостановлена.
- `/stop` — приостановить рассылку для этого chat_id. Сами поисковые запросы
  в `searches.json` при этом не трогаются — просто уведомления по всем
  поискам этого получателя перестают приходить, пока не пришлёте `/start`.

## searches.json

Несколько поисков (областей/фильтров) — по одному элементу на каждый.
`url` — обычная ссылка на карту krisha.kz, скопированная из адресной строки браузера
(фильтры `das[...]` + `lat`/`lon`/`zoom`). Область просмотра карты пересчитывается
в параметр `bounds` автоматически. `chat_id` — получатель уведомлений по этому
поиску (число, см. «Команды боту» выше); один человек с несколькими поисками
просто повторяет свой `chat_id` в каждой записи.

```json
{
  "searches": [
    { "name": "Центр",  "url": "https://krisha.kz/map/arenda/kvartiry/?das[...]&zoom=14&lat=43.24776&lon=76.93696", "enabled": true, "chat_id": 123456789 },
    { "name": "Орбита", "url": "https://krisha.kz/map/arenda/kvartiry/?...", "enabled": false, "chat_id": 987654321 }
  ]
}
```

Файл перечитывается в начале каждого цикла — правки применяются без рестарта
контейнера. `enabled: false` выключает поиск, не удаляя его. Имя поиска попадает
в уведомление. Новый поиск сначала проходит свою тихую базу. Если у записи
отсутствует или невалиден `chat_id` (как у плейсхолдера `TODO_REPLACE_WITH_REAL_CHAT_ID`
в примере из репозитория) — файл целиком не подхватывается, сервис работает на
предыдущей валидной версии; если валидной версии ещё не было, поиски просто не
запускаются (в лог идёт предупреждение), но сам сервис не падает — `/start` и
`/stop` продолжают отвечать.

Для GitHub Actions этот файл можно вообще не редактировать — см. `SEARCHES_JSON`
ниже: переменная того же формата, которая полностью подменяет `searches.json`
без коммита.

### Миграция с однопользовательской версии

Раньше был единственный `state.chat_id`, определяемый по `TARGET_TG_USERNAME`.
Теперь получатель задаётся в `searches.json`. Перед обновлением существующего
деплоя вручную впишите `chat_id` в каждую запись `searches.json` — значение
можно взять из старого `state.json`/gist (поле `chat_id`, теперь неиспользуемое)
либо получить заново через `/start`.

## Состояние

`./data/state.json` (том Docker): флаги тихой базы по поискам, список уже
виденных объявлений, список chat_id на паузе (`paused`) и курсор `getUpdates`
для команд (`update_offset`, нужен именно из-за режима `--once`, где процесс
каждый раз новый). Удаление файла приводит к повторной тихой базе (без шторма
уведомлений) и сбросу пауз.

## Отладка

```bash
# один цикл без отправки в Telegram, всё в лог
DRY_RUN=1 RUN_ONCE=1 docker compose run --rm krishabeholder

# локально без Docker (нужны Python 3.11+, pip install -r requirements.txt)
set STATE_PATH=data/state.json
set SEARCHES_PATH=searches.json
python -m app.main --once --dry-run

# самопроверка группировки уведомлений по chat_id (без сети)
python scripts/selfcheck_grouping.py
```

## Автономный запуск в GitHub Actions (бесплатно)

Сервис умеет работать без своего сервера: раз в 30 минут его запускает
`.github/workflows/beholder.yml` (`python -m app.main --once`), а состояние
хранится в приватном GitHub Gist (`GIST_ID` + `GIST_TOKEN`), потому что файловая
система раннера очищается после каждого прогона.

Что задать в репозитории (**Settings → Secrets and variables → Actions**):

| Имя | Тип | Значение |
|-----|-----|----------|
| `TELEGRAM_BOT_TOKEN` | Secret | токен от @BotFather |
| `GIST_TOKEN` | Secret | Fine-grained PAT с правом **Gists: Read and write** |
| `GIST_ID` | Secret | id созданного приватного gist |
| `SEARCHES_JSON` | Variable | получатели и поиски — см. ниже |
| `ADMIN_CHAT_ID` | Variable | *(необязательно)* chat_id для алертов о деградации сервиса |
| `MAX_PAGES` / `PAGE_DELAY_S` | Variable | *(необязательно)* тонкая настройка |

### Получатели и поиски без коммитов — SEARCHES_JSON

`SEARCHES_JSON` — repository variable с тем же содержимым, что и `searches.json`
(см. раздел выше), одной строкой. Если она задана — используется вместо файла
из репозитория, и правится прямо в **Settings → Secrets and variables →
Actions → Variables**, без коммита. Следующий прогон (по расписанию или
вручную через **Actions → KrishaBeholder → Run workflow**) сразу подхватывает
новое значение — это и есть основной способ добавлять/менять получателей и
поиски для GitHub Actions.

Порядок для нового получателя:
1. Он пишет боту `/start` — бот отвечает его числовым `chat_id`.
2. Вы добавляете в JSON новую запись `{ "name": ..., "url": ..., "enabled": true, "chat_id": <это число> }`
   (несколько поисков одного человека — несколько записей с одинаковым `chat_id`).
3. Вставляете весь JSON целиком в значение переменной `SEARCHES_JSON` и сохраняете.
4. По желанию — сразу **Run workflow**, чтобы не ждать до 30 минут; иначе подхватится на ближайшем cron.

Лимит GitHub на значение repository variable — 48 КБ, для личного бота с
десятками поисков этого с большим запасом хватает.

Порядок самого первого запуска: создать gist → прописать секреты (`TELEGRAM_BOT_TOKEN`,
`GIST_ID`, `GIST_TOKEN`) → вручную запустить workflow, чтобы бот поднялся и начал
принимать `/start`, даже если `SEARCHES_JSON` ещё пустая → получатели пишут `/start`
→ собрать их `chat_id` в JSON и вписать в `SEARCHES_JSON`, как описано выше.

`searches.json` в самом репозитории при этом остаётся как запасной вариант
(используется, только если `SEARCHES_JSON` не задана) и как файл для
Docker/локального запуска — коммитить его для GitHub Actions больше не
обязательно. Если всё же правите его — учтите, что там появляются числовые
Telegram chat_id получателей: сами по себе не секрет (без токена бота ими
нельзя воспользоваться), но не полностью анонимные данные, если репозиторий
публичный.

## Замечания

- Запускать только один экземпляр на один бот-токен (иначе конфликт getUpdates 409).
- Если объявлений в поиске больше `MAX_PAGES × 20`, хвост не обходится
  (в логе будет предупреждение) — стоит сузить фильтры или уменьшить область.
- Поднятые/продлённые объявления с тем же id повторно не присылаются.
- В GitHub Actions расписание `cron` — «по возможности»: реальные запуски могут
  задерживаться на 5–20 минут под нагрузкой, отдельные слоты пропускаются.
- Scheduled workflow отключается после 60 дней без активности в репозитории —
  изредка делайте любой коммит (или включайте обратно по письму от GitHub).
- Если из дата-центров GitHub (США) krisha.kz отвечает ошибками/капчей, это будет
  видно в логах прогона — тогда лучше вернуться к варианту с постоянным сервером.
