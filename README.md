# KrishaBeholder

Сервис мониторинга новых объявлений об аренде квартир на krisha.kz.
Раз в 30 минут (с небольшим случайным сдвигом) обходит заданные поиски и присылает
новые объявления в Telegram.

## Запуск

1. Скопировать `.env.example` в `.env`, вписать `TELEGRAM_BOT_TOKEN`.
2. Проверить/отредактировать `searches.json` (см. ниже).
3. `docker compose up -d --build`
4. Написать боту `/start` с аккаунта `@black_mug` (или указанного в `TARGET_TG_USERNAME`) —
   сервис определит chat_id, сохранит его и ответит подтверждением.
   Важно: сообщение боту нужно отправить **после** запуска сервиса
   (история getUpdates хранится недолго).

Первый обход каждого поиска — «тихая база»: существующие объявления запоминаются
без уведомлений, дальше приходят только реально новые.

## searches.json

Несколько поисков (областей/фильтров) — по одному элементу на каждый.
`url` — обычная ссылка на карту krisha.kz, скопированная из адресной строки браузера
(фильтры `das[...]` + `lat`/`lon`/`zoom`). Область просмотра карты пересчитывается
в параметр `bounds` автоматически.

```json
{
  "searches": [
    { "name": "Центр",  "url": "https://krisha.kz/map/arenda/kvartiry/?das[...]&zoom=14&lat=43.24776&lon=76.93696", "enabled": true },
    { "name": "Орбита", "url": "https://krisha.kz/map/arenda/kvartiry/?...", "enabled": false }
  ]
}
```

Файл перечитывается в начале каждого цикла — правки применяются без рестарта
контейнера. `enabled: false` выключает поиск, не удаляя его. Имя поиска попадает
в уведомление. Новый поиск сначала проходит свою тихую базу.

## Состояние

`./data/state.json` (том Docker): найденный `chat_id`, флаги тихой базы по поискам
и список уже виденных объявлений. Удаление файла приводит к повторной тихой базе
(без шторма уведомлений).

## Отладка

```bash
# один цикл без отправки в Telegram, всё в лог
DRY_RUN=1 RUN_ONCE=1 docker compose run --rm krishabeholder

# локально без Docker (нужны Python 3.11+, pip install -r requirements.txt)
set STATE_PATH=data/state.json
set SEARCHES_PATH=searches.json
python -m app.main --once --dry-run
```

## Автономный запуск в GitHub Actions (бесплатно)

Сервис умеет работать без своего сервера: раз в 30 минут его запускает
`.github/workflows/beholder.yml` (`python -m app.main --once`), а состояние
хранится в приватном GitHub Gist (`GIST_ID` + `GIST_TOKEN`), потому что файловая
система раннера очищается после каждого прогона.

Что задать в репозитории (**Settings → Secrets and variables → Actions**):

| Имя | Тип | Значение |
|-----|-----|----------|
| `TELEGRAM_BOT_TOKEN` | Secret | токен от @BotFather |
| `GIST_TOKEN` | Secret | Fine-grained PAT с правом **Gists: Read and write** |
| `GIST_ID` | Secret | id созданного приватного gist |
| `TARGET_TG_USERNAME` | Variable | ник в Telegram, чьё `/start` принимается (без `@`) |
| `MAX_PAGES` / `PAGE_DELAY_S` | Variable | *(необязательно)* тонкая настройка |

`chat_id` **не задаётся вручную**: при первом прогоне сервис определяет его по
`/start` от `TARGET_TG_USERNAME` и сохраняет в gist. Дальше поиск не выполняется.
Полностью убрать chat_id нельзя — Telegram Bot API требует числовой адрес чата в
`sendMessage` и не умеет слать по нику; ник → chat_id знает только сам Telegram
после первого сообщения боту.

Порядок первого запуска: создать gist → прописать секреты/переменные → написать
боту `/start` → вручную запустить workflow (**Actions → KrishaBeholder → Run
workflow**). Первый прогон определит chat_id и «тихо» запомнит текущие объявления,
дальше по расписанию приходят только новые.

`searches.json` лежит в репозитории (это не секрет) — правьте прямо там.

## Замечания

- Запускать только один экземпляр на один бот-токен (иначе конфликт getUpdates 409).
- Если объявлений в поиске больше `MAX_PAGES × 20`, хвост не обходится
  (в логе будет предупреждение) — стоит сузить фильтры или уменьшить область.
- Поднятые/продлённые объявления с тем же id повторно не присылаются.
- В GitHub Actions расписание `cron` — «по возможности»: реальные запуски могут
  задерживаться на 5–20 минут под нагрузкой, отдельные слоты пропускаются.
- Scheduled workflow отключается после 60 дней без активности в репозитории —
  изредка делайте любой коммит (или включайте обратно по письму от GitHub).
- Если из дата-центров GitHub (США) krisha.kz отвечает ошибками/капчей, это будет
  видно в логах прогона — тогда лучше вернуться к варианту с постоянным сервером.
